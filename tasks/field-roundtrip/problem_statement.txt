Preserve the declared types and exact values of additional user and session fields when Better Auth serializes and restores them. A field configured with type "string" may legitimately contain "2024-01-02T03:04:05Z". It must remain that exact string, rather than becoming a Date or acquiring normalized timestamp formatting. The same rule applies to string elements in "string[]" fields and strings inside "json" fields, including nested objects and arrays whose keys resemble built-in timestamp names.

Apply this behavior to auth.api.signUpEmail results and auth.api.getSession results. Cover database adapters that serialize arrays or JSON because they lack native support, secondaryStorage returning either JSON strings or pre-parsed objects, and session.cookieCache using compact, jwt or jwe. For jwt, cover both default secret-based signing and jwt({ sessionCookieCache: true }). Enabling a cache must not change the runtime types or contents of these fields. A valid, unexpired cookie cache must serve these fields without rereading the backing user or session records.

When auth.api.updateUser or auth.api.updateSession rewrites secondary-stored sessions, unrelated existing fields must retain their original types and values on subsequent retrieval. Preserve nulls, empty arrays and ordinary JSON values throughout these round trips.

Continue returning genuine Date objects for built-in user and session timestamps and additional fields explicitly configured as type "date". Keep existing authentication, expiry handling and output-field filtering behavior. Client-side response parsing, standalone getCookieCache behavior and new public auth configuration options are outside scope.
